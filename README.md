# Дашборд по домам — общая разметка

Одна страница по одному постоянному адресу. Открывают двое, размечают
оба, отметки и заметки видны обоим и сохраняются сами.

```
браузер  ──→  Cloudflare Pages   страница (public/index.html)
             ↕ /api/marks        функция синхронизации
             D1                  отметки, с журналом правок
```

Репозиторий держит **только развёртывание**. Генератор страницы,
выгрузки и данные остались в задаче (`Task - search house in
Kaliningrad`): переносить их сюда значило бы раздвоить библиотеку,
общую с квартирной задачей.

## Как это устроено

**Отметка привязана к id объявления** вида `domclick:https://…` —
источник плюс ссылка без параметров. Ключ детерминированный, поэтому
пересборка страницы с новыми объектами и другим оформлением накопленную
разметку не роняет.

**Ключ переживает смену источника-победителя.** Один и тот же дом лежит
на нескольких площадках; слияние оставляет победителя, а он между
выгрузками меняется — и ключ вместе с ним. Строка поэтому знает и
запасные ключи, по каждой своей ссылке: разметка под старым показывается
как своя, а переезжает на новый только при живой правке человека.
Переносить на загрузке нельзя — запись ушла бы в журнал от лица того,
кто просто открыл страницу.

**Правки уходят по полям, а не записями.** Человек ставит метку — на
сервер уезжает только цвет. Отсутствие поля в запросе значит «не
трогай», явный `null` — «стёрто». Если отправлять запись целиком, метка
увозит с собой устаревшую копию чужой заметки и молча её затирает.
Это уже случалось; проверка `check-sync.js` держит случай под контролем.

**В шапке страницы стоит момент выкладки.** Его ставит хук `pre-commit`
и только тогда, когда в коммит попадает сам `public/index.html`: правка
README и ночной снимок разметки страницу не меняют, и двигать отметку
не должны — отметка, которая шевелится без причины, перестаёт что-либо
значить на второй неделе. В атрибуте `datetime` лежит UTC, а показывает
страница время читателя с его поясом: отец в Калининграде и Алексей в
Екатеринбурге иначе увидели бы одно число и поняли его по-разному.

**Каждая правка попадает в журнал** (`marks_log`). Пока вход на страницу
не закрыт, ссылка равна праву записи — откатить порчу можно только по
журналу и по ежедневному снимку в `backup/`.

## Первая настройка

Node на этой машине портативный и в PATH его нет, поэтому `npx` не
работает. Все команды wrangler зовутся через обёртку `cf.cmd` из этой
папки — она подставляет нужный node сама.

```bat
cf login
cf d1 create dom-kgd-marks
```

Полученный `database_id` вписать в `wrangler.toml`, затем:

```bat
cf d1 execute dom-kgd-marks --remote --file=schema.sql
cf pages project create dom-kgd-2be42d1d18 --production-branch main
cf pages secret put SYNC_TOKEN
cf pages deploy
```

`SYNC_TOKEN` — содержимое `.sync-token` (файл не коммитится). Он же
вшивается в страницу при сборке, поэтому значения обязаны совпадать.

Отдельно — один раз на каждый клон:

```bat
git config core.hooksPath tools/hooks
```

Эта команда включает **оба** хука, и без неё они не работают вовсе:

- `pre-commit` — проставляет в шапке страницы момент выкладки;
- `pre-push` — публикует страницу на Pages (см. «Обычный цикл» ниже).

Хуки лежат в репозитории, а не в `.git/hooks`, потому что `.git/hooks`
не версионируется: они существовали бы в одном экземпляре на одной
машине и терялись при клонировании молча. Ценой за это — одна команда
на клон. Без неё коммиты и пуши проходят, но отметка остаётся от
прошлой выкладки, **а страница не публикуется вообще**. Проверить:
`git config core.hooksPath` должен ответить `tools/hooks`.

## Обычный цикл работы

```bat
rem из папки задачи: пересобрать страницу с данными
node tools\dashboard-houses.js

rem проверить перед выкладкой
node ..\tools\check-dashboard.js Rep\public\index.html
cd Rep && node tools\check-sync.js

git add -A && git commit -m "данные на 21 августа" && git push
```

**`git push` и есть выкладка** — её делает хук `pre-push`. Отдельной
команды помнить не нужно, но понимать, что происходит, нужно.

Сам по себе push страницу не публикует и никогда не публиковал: проект
Pages создан как direct-upload (`Git Provider: No` в `cf pages project
list`), GitHub к нему не подключён и пушей не видит — ни через минуту,
ни через час. Публикует только `pages deploy`, и хук зовёт именно её.

Пока это была отдельная строка в README, случилось ровно то, чего такие
связки и стоят: 2026-08-20 два коммита ушли в GitHub, а живая страница
осталась пятичасовой давности и выглядела при этом свежей.

Что делает хук:

- срабатывает **только на `main`** и только если в пушимом действительно
  менялся `public/index.html` — пересборка с теми же данными файл не
  трогает, и публиковать нечего;
- выкладывает **до** push. Провал выкладки останавливает push: коммиты
  остаются локальными, страница не тронута — это согласованное
  состояние. Обратный порядок хук устроить не может, `post-push` в git
  не существует;
- после выкладки спрашивает у Cloudflare, что теперь в продакшне, и
  сверяет с коммитом. «Команда отработала» и «в бою лежит нужное» —
  разные вещи.

Не публиковать этот push: `SKIP_DEPLOY=1 git push`.
Посмотреть, что хук собирается сделать: `DEPLOY_DRY=1 git push`
(push при этом тоже не выполнится).

Проверить руками в любой момент: `cf pages deployment list
--project-name dom-kgd-2be42d1d18` — колонка `Source` против `git
rev-parse --short HEAD`. Не совпало — выкладки не было.

Адрес не меняется никогда — ссылку у отца менять не нужно.

**Страница ровно одна.** Генератор без флагов пишет прямо сюда, в
`public/index.html`. Отдельный датированный слепок снимается явным
`--archive` и кладётся в папку задачи: он работает без сервера и без
токена, разметка в нём своя, и в репозиторий он не едет.

## Перенос разметки из локального файла

```bat
node tools\import-marks.js dom-kaliningrad-otmetki.json --url https://<адрес>/api/marks
node tools\import-marks.js dom-kaliningrad-otmetki.json --url https://<адрес>/api/marks --apply
```

Первая команда — сухой прогон: сколько отметок легло на объекты и
сколько повисло. Повисшие (объявление сменило ссылку или ушло из выдачи)
выгружаются в `backup/orphans-<дата>.json` и при записи сохраняются
тоже — объявление может вернуться.

Принимаются оба носителя: `.json` от кнопки «Только отметки» и `.html`
от «Сохранить страницу с отметками».

## Проверки

| Команда | Что доказывает |
|---|---|
| `node ..\..\..\tools\lib\review-table.js` | обвязка таблицы и слой синхронизации, 74 проверки |
| `node ..\..\tools\check-dashboard.js Rep\public\index.html` | страница жива в браузере: фильтры, метки, заметки |
| `node ..\tools\check-sources.js` | у объекта показаны ВСЕ его площадки, а разметка не теряется при смене источника-победителя |
| `node tools\check-sync.js` | **Edge и Chrome видят разметку друг друга**, она переживает перезагрузку у обоих, а фильтры и сортировка работают у каждого свои — 22 проверки |
| `node tools\stamp-updated.js --self` | разметка отметки и пересчёт поясов, 15 проверок |
| `node tools\backup-marks.js --url …` | снимок разметки в `backup/` |

`check-sync.js` поднимает локальный сервер с локальной базой и ничего
не пишет в боевую разметку. Базу он пересоздаёт целиком: остатки
прошлого прогона делают стенд зелёным на сломанном коде.

## Что здесь намеренно неудобно

- **Фильтры и сортировка не общие и не сохраняются.** Страница всегда
  открывается на порогах брифа. Это решение, а не забытая функция: двое
  обязаны видеть одинаковую стартовую картину, иначе спорят о разных
  списках, каждый уверенный, что смотрит на «весь список». Общее здесь
  только то, что решает человек, — метки и заметки.
- **Правку по строке, в которой стоит курсор, человек увидит после того,
  как из неё уйдёт.** Опрос не трогает поле под курсором — иначе чужая
  метка затирала бы текст на полуслове.
- **Побеждает более поздняя правка.** Двое, правящие одну и ту же
  заметку одновременно, получат версию того, кто закончил вторым.
  Разные поля и разные объекты не конфликтуют вовсе.
- **Вход на страницу не закрыт.** Любой, кому попадёт ссылка, может
  править разметку. Защита — неугадываемый адрес, журнал и бэкап.
  Закрывается включением Cloudflare Access на две почты; страницу для
  этого менять не нужно, обработка истёкшей сессии в ней уже есть.
